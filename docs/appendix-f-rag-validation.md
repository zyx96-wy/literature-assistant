## F.1 验证目标

验证目标：

1. 验证 RAG 在学术文献问答场景的可行性
2. 验证跨文档聚合问题能否通过多路检索解决
3. 验证引用追踪、References 过滤等关键能力的可实现性
4. 识别传统 RAG 的架构边界

## F.2 技术方案

**工具栈：**

| 组件 | 选型 | 说明 |
|---|---|---|
| 编排 | Dify Chatflow | 可视化流程编排 |
| 生成模型 | qwen3.7-plus | 问题改写 + 最终回答 |
| Embedding | text-embedding-v3 | 向量检索 |
| Rerank | qwen3-rerank | 重排序 |
| 知识库 | Dify 内置知识库 | 3 篇学术论文 |

**分段策略：**

| 参数 | 值 | 说明 |
|---|---|---|
| 分段标识符 | `\n\n` | 按段落切分 |
| 分段最大长度 | 500 字符 | 经优化从 800 降到 500 |
| 分段重叠 | 80 字符 | 防止边界信息丢失 |
| 预处理 | 替换连续空格换行 | — |

**检索策略：**

| 参数 | 值 |
|---|---|
| 检索方式 | 混合检索（向量 + 关键词） |
| Top K | 单路 8；多路每路 4 |
| Score 阈值 | 0.3 |
| Rerank | qwen3-rerank |

**流程架构：**
用户问题
↓
问题分类器（clarify / targeted / search / compose / general）
├─ clarify → 直接回复（澄清 / 拒答）
├─ targeted → 单检索 → 代码执行 → LLM → 回复
├─ search → 问题改写 → 拆分查询 → 3 路并行检索 → 合并 → LLM → 回复
├─ compose → 共用 general 分支
└─ general → 单检索 → 代码执行 → LLM → 回复

**多路检索分支（search）详解：**

问题改写（LLM 2）
↓ 输出 3 行查询
拆分查询（代码执行 2）
↓ 输出 query1 / query2 / query3
3 路并行检索
↓ 每路 Top K=4
合并结果（代码执行 3）
↓ References 过滤 + 按来源分组
最终 LLM
↓ 引用追踪 + 综合回答

## F.4 优化过程（5 轮）

| 轮次 | 优化动作 | 效果 |
|---|---|---|
| 第 1 轮 | 分段 800 → 500 | 单文档第三项不再丢失 |
| 第 2 轮 | 开启 Rerank（qwen3-rerank） | 多跳题准确率从 50% → 100% |
| 第 3 轮 | Prompt 加「综合多块」规则 | 多跳题不再只看第一块 |
| 第 4 轮 | References 过滤 + 代码节点按来源分组 | 跨文档题不再引用参考文献人名 |
| 第 5 轮 | **多路检索**（核心改动） | 跨文档题从 0% → 100% |

## F.6 核心发现

**发现 1：单检索节点 + 多行查询 = 召回偏向**

- 问题改写输出 3 行查询，整段丢进单检索节点
- embedding 偏向某一行，导致跨文档题只召回 2 篇
- 解决：拆成 3 条独立查询，3 路并行检索

**发现 2：References 段污染上下文**

- 学术 PDF 的参考文献段有大量人名、年份，向量匹配度高
- 抢占 Top K 名额，导致回答出现「Noble 的《算法的压迫》」等 References 内容
- 解决：代码节点过滤前 200 字符包含 `References` / `参考文献` 的块

**发现 3：代码节点分组不当**

- 同一篇论文的多块被编成多个编号 `[1][2][3]`
- LLM 误以为是多篇文档，回答「4 篇文档没有共通点」（实际只有 3 篇）
- 解决：同一来源的多块合并到一个编号下

**发现 4：用户问题无法跨节点引用**

- 问题改写节点的上游是分类器，不是「开始」
- Dify 变量列表看不到 `query`
- 解决：用「上下文」字段手动绑 `{{#用户输入.query#}}`

**发现 5：SYSTEM 和 USER 的角色分工**

- 把参考文档、要求、用户问题全写进 SYSTEM，USER 留空 → LLM 输出空
- 解决：SYSTEM 只写角色设定，USER 写文档 + 要求 + 问题

## F.7 对产品的影响

**检索问答模块（9.3）：**

- 分段策略：500 字符 + 80 重叠，已在 Dify 验证有效
- 检索配置：混合检索 + Rerank + Top K=8 + 阈值 0.3
- References 过滤：代码节点过滤参考文献段
- 引用追踪：LLM「上下文」字段绑检索 result

**问答助手模块（9.4）：**

- 一问一答：Dify 里已验证
- 引用追踪：`【来源：文档名】` 格式，可点击回原文
- 有限多轮：Dify 默认不支持，需在代码实现

**综述生成模块（9.6）：**

- 综述走 `search` 分支（多路检索）
- Prompt 要求每个论点带「（支持：N篇）」+ 薄弱/争议标注
- 依赖多路检索的三篇论文同时召回

**V3 复现模式、模型卡片：**

- 需要实体关系推理（如「谁用了 X 方法」）
- 传统 RAG 不支持
- 需要 GraphRAG 或分层摘要

## F.8 下一步优化

**优化方向 1：GraphRAG**

- 适用场景：30+ 篇文档的全局总结、实体关系推理
- 候选工具：InfraNodus / LightRAG / Microsoft GraphRAG
- 验证方式：小样本 PoC，对比传统 RAG 与 GraphRAG 的效果

**优化方向 2：代码实现**

- Dify 是原型验证，精确逻辑需用代码实现
- 已有 `intent_classifier.py` 设计：5 类分类 + 优先级路由 + 多轮继承
- 后续实现：RAG 检索链路 + 引用追踪 + 综述生成

**优化方向 3：References 过滤精细化**

- 当前只过滤文末 References 段
- 正文里的引文（「Noble (2018) 指出」）尚未处理
- 需要更精细的识别逻辑

**优化方向 4：多轮意图继承**

- Dify 分类器不支持对话历史
- 代码设计里通过 `history` 参数实现
- 用户说「那篇」时继承上一轮的文献范围
